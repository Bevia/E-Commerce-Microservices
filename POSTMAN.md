# Postman end-to-end test guide

This runbook tests the three Spring Boot services running through Docker Compose:

- Authentication service: user registration, sign-in, and JSON Web Token (JWT) issuance.
- Order service: create, retrieve, list, update, and delete orders.
- Payment service: process, retrieve, list, update, and delete payments.

The requests below exercise the system as it exists today. Payment processing is currently a separate client request: completing a payment does **not** automatically update its order from `PENDING` to `PAID`. The guide includes a manual order-status update so the complete test can finish in a consistent state.

Validation status on 27 August 2026:

- Health, signup, sign-in, all order endpoints, all payment endpoints, authorization rejection, and cleanup passed against the running Docker containers.
- Order reads return explicit response Data Transfer Objects (DTOs). Their `orderItems` are fetched and mapped while the database transaction is active, so they remain serializable when Open Session in View is disabled.
- Payment lookup by order identifier returns the newest payment attempt when retries have created more than one payment row for the same order.

## 1. Prerequisites

- Docker Desktop is running.
- The three Docker Compose containers are running and healthy.
- Postman is installed.

From the repository root, start or confirm the services:

```bash
docker compose up -d
docker compose ps
```

Expected local addresses:

| Service | Address on the Mac | Port inside the container |
|---|---|---|
| Authentication | `http://localhost:8083` | `8083` |
| Order | `http://localhost:8090` | `8080` |
| Payment | `http://localhost:8081` | `8081` |

The order service uses `localhost:8090` because another local Nginx container already uses host port `8080`.

## 2. Create the Postman environment

Create an environment named `E-Commerce Docker Local` with these variables:

| Variable | Initial value | Purpose |
|---|---|---|
| `authBaseUrl` | `http://localhost:8083` | Authentication service |
| `orderBaseUrl` | `http://localhost:8090` | Order service |
| `paymentBaseUrl` | `http://localhost:8081` | Payment service |
| `password` | `password123` | Test-user password |
| `username` | leave empty | Generated by the signup request |
| `email` | leave empty | Generated by the signup request |
| `token` | leave empty | Saved after sign-in |
| `userId` | leave empty | Saved after sign-in |
| `orderId` | leave empty | Saved after order creation |
| `paymentId` | leave empty | Saved after payment processing |

Select this environment before sending requests.

## 3. Create the Postman collection

Create a collection named `E-Commerce Microservices - Docker`.

At collection level, configure:

```text
Authorization type: Bearer Token
Token: {{token}}
```

Protected order and payment requests should use **Inherit auth from parent**. Health, signup, and sign-in requests should use **No Auth**.

Run the requests in the order shown below. The scripts automatically pass identifiers and the token to subsequent requests.

## 5. Authentication flow

### 5.1 Register a unique user

```text
POST {{authBaseUrl}}/api/auth/signup
Authorization: No Auth
Content-Type: application/json
```

Pre-request script:

```javascript
const suffix = Date.now();
pm.environment.set("username", `postman_${suffix}`);
pm.environment.set("email", `postman_${suffix}@example.com`);
```

Body, using **raw JSON**:

```json
{
  "username": "{{username}}",
  "email": "{{email}}",
  "password": "{{password}}"
}
```

Tests:

```javascript
pm.test("User is registered", function () {
    pm.response.to.have.status(200);
    pm.expect(pm.response.json().message).to.eql("User registered successfully!");
});
```

The role is optional. When omitted, the application assigns `ROLE_USER`.

### 5.2 Sign in and save the token

```text
POST {{authBaseUrl}}/api/auth/signin
Authorization: No Auth
Content-Type: application/json
```

Body:

```json
{
  "username": "{{username}}",
  "password": "{{password}}"
}
```

Tests:

```javascript
pm.test("Sign-in succeeds and returns a token", function () {
    pm.response.to.have.status(200);

    const response = pm.response.json();
    pm.expect(response.token).to.be.a("string").and.not.empty;
    pm.expect(response.type).to.eql("Bearer");
    pm.expect(response.id).to.be.a("number");
    pm.expect(response.username).to.eql(pm.environment.get("username"));
    pm.expect(response.roles).to.include("ROLE_USER");

    pm.environment.set("token", response.token);
    pm.environment.set("userId", response.id);
});
```

The token expires after one hour. Run sign-in again if protected requests begin failing after that time.

## 6. Order flow

All requests in this section use the collection's Bearer Token authorization.

### 6.1 Create an order

```text
POST {{orderBaseUrl}}/api/orders
Content-Type: application/json
```

Body:

```json
{
  "userId": {{userId}},
  "customerName": "Postman Test Customer",
  "totalAmount": 89.50
}
```

Tests:

```javascript
pm.test("Order is created as PENDING", function () {
    pm.response.to.have.status(201);

    const response = pm.response.json();
    pm.expect(response.id).to.be.a("number");
    pm.expect(response.userId).to.eql(Number(pm.environment.get("userId")));
    pm.expect(response.username).to.eql(pm.environment.get("username"));
    pm.expect(response.status).to.eql("PENDING");
    pm.expect(Number(response.totalAmount)).to.eql(89.5);

    pm.environment.set("orderId", response.id);
});
```

Current implementation note: `customerName` is accepted by the request object but is not stored on the `Order` entity.

### 6.2 List all orders

## 7. Payment flow

### 7.1 Process a payment

```text
POST {{paymentBaseUrl}}/api/payments/process
Content-Type: application/json
```

Body:

```json
{
  "orderId": "{{orderId}}",
  "amount": 89.50,
  "currency": "EUR",
  "paymentMethod": "TEST_CARD"
}
```

Tests:

```javascript
pm.test("Payment is completed", function () {
    pm.response.to.have.status(201);

    const response = pm.response.json();
    pm.expect(response.id).to.be.a("number");
    pm.expect(response.orderId).to.eql(String(pm.environment.get("orderId")));
    pm.expect(Number(response.amount)).to.eql(89.5);
    pm.expect(response.currency).to.eql("EUR");
    pm.expect(response.paymentMethod).to.eql("TEST_CARD");
    pm.expect(response.status).to.eql("COMPLETED");
    pm.expect(response.transactionId).to.match(/^TXN_/);
    pm.expect(response.paymentDate).to.be.a("string");

    pm.environment.set("paymentId", response.id);
});
```

## 9. Security test

Duplicate the `GET {{orderBaseUrl}}/api/orders/{{orderId}}` request, change Authorization to **No Auth**, and send it.

Test:

```javascript
pm.test("Protected endpoint rejects a missing token", function () {
    pm.expect(pm.response.code).to.be.oneOf([401, 403]);
});
```

Spring Security may return either `401 Unauthorized` or `403 Forbidden` depending on the configured authentication entry point. Any successful `2xx` response would be a security failure.

## 12. Troubleshooting

### Connection refused

Confirm Docker Compose is running:

```bash
docker compose ps
```

Every service should report `healthy`.

### `400 Bad Request` during signup

The username or email probably already exists. Send the signup request again; its pre-request script generates a new value each time.

### `401 Unauthorized` or `403 Forbidden`

- Confirm the request inherits collection authorization.
- Confirm the collection token is `{{token}}`.
- Run sign-in again to refresh the one-hour token.
- Confirm the same `JWT_SECRET` value is configured for all three containers.

### Order request uses the wrong port

Use `{{orderBaseUrl}}`, which is `http://localhost:8090` in this Docker Compose environment. Container port `8080` is published as host port `8090`.

### Data disappears

Each service currently uses an H2 in-memory database. Recreating or removing a container resets that service's data. Run the collection from signup again after a reset.

### Payment succeeds but order remains `PENDING`

This is expected in the current implementation. Payment and order status are not automatically synchronized. Run the manual `PUT /api/orders/{id}/status?status=PAID` request, or implement the future synchronous or event-driven integration.

### Authenticated requests return `403 Forbidden`

Run sign-in again and confirm that the request inherits the collection's Bearer Token authorization. Order tokens expire after one hour. If a fresh token still fails, inspect the relevant service log for the underlying application exception.
